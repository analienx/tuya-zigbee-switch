### Non-PM OTA preflight compatibility

The generic targeted OTA runner normally requires a fresh numeric `power` field to enforce the PM load ceiling. This TS011F-BS Client has no metering sensor. The runner then requires the fresh MQTT device IEEE and relay state but exempts **only this precise non-PM variant** from the power check; PM and all other image classes still fail closed if numeric metering is absent. An unexpected `power` property also blocks this non-PM exception.

Use only the targeted one-entry OTA index and bounded block size. ### Repeatable link qualification and recovery workflow (2026-09-21)

The previous one-successful-read preflight was insufficient: a subsequent OTA check timed out and two later GETs failed. The host-only `helper_scripts/bseed_nonpm_link_gate.py` now samples **three** target-only relay GETs separated by at least 25 seconds (default 30 seconds), accepting only non-retained, IEEE/build/relay/policy-matched states within 12 seconds of each request. This is a limited MQTT communication proxy, not proof of a correlated ZCL response or long-term parent stability. Retained `online` and historical `last_seen` are diagnostic context, never pass conditions. A failure stops further probes within that run and writes private evidence with the specific failure.

The private profile must pin `preflash_build` and `preflash_relay_physical_mode`, in addition to `non_pm: true`, `require_pm: false`, relay `state_relay` and the exact preflash identity. Run the following **separate, deliberate commands** in the repository root, replacing PRIVATE.json with the existing exact-device private profile:

```text
python helper_scripts/bseed_ota_campaign.py --profile PRIVATE.json --mode link-gate
python helper_scripts/bseed_ota_campaign.py --profile PRIVATE.json --mode check
python helper_scripts/bseed_ota_campaign.py --profile PRIVATE.json --mode link-gate
# Flash remains a separate explicitly authorized action, NEVER automatic:
python helper_scripts/bseed_ota_campaign.py --profile PRIVATE.json --mode flash --confirm-ieee EXACT_TARGET_IEEE
```

The private `LATEST_LINK_GATE.json` pointer is invalidated at the beginning of each attempt; each completed attempt also gets its own immutable `link_gate_<UUID>.json`. Non-PM `check`/`flash` refuse absent, failed, expired (>600 s), wrong-device/build/hash or too-closely-spaced evidence. Flash requires an entirely new qualified series **starting after** the successful `LAST_CHECK.json` timestamp, in addition to the existing 30-minute check validity. Starting a new OTA eligibility check archives the old success before issuing the request: a failed check cannot leave a previous success eligible for flash. If an attempt is interrupted, inspect its latest private evidence and do not reuse an older pass.

**Recovery decisions:** If even one link sample fails, stop before checking OTA: inspect target-only Zigbee2MQTT errors, exact IEEE last-seen progression, parent/neighbor evidence and physical red-LED observation. A single successful read following a failure is not enough to retry OTA. If all three link samples pass but the target-only OTA check fails, treat the cause as **unresolved OTA-query or intermittent transport**, not proven parent loss; preserve the check transaction/error and diagnose the installed `cli4` OTA service separately. A second check is not an automated retry. No script in this path changes the coordinator, router, channel, global settings, relay, pairing state or supply power.

If physical recovery becomes necessary, verify the connected load and circuit first; any power-cycle, scoped rejoin or targeted re-interview requires separate operator authorization and a new link gate afterwards. Never remove the device or open global permit-join as a shortcut. A green preflash gate does **not** authorize release: successful one-target OTA must still undergo the existing re-interview, exact installed build and settings/binding readback, physical load/relay and sustained parent stability checks. Keep the existing `cli5-rc1` image SHA and rollback unchanged; only host-side diagnostic/orchestration code is modified here.

**Single-command option:** With the private image server already running and independently verified, run `python helper_scripts/bseed_ota_campaign.py --profile PRIVATE.json --mode qualify`. This orchestrates the same three read-only stages (`link-gate`, `check`, `link-gate`) serially and **never calls flash**, regardless of outcome. The first error stops the sequence; an old successful check is archived at entry. The command's `QUALIFICATION_PASSED_NO_FLASH` result means only that these immediate communication/OTA-query gates passed; it is not hardware acceptance or permission to interrupt an unidentified appliance. Re-run qualification if its 10-minute link evidence or 30-minute OTA-check record expires; do not use a stale pass to start an update.
