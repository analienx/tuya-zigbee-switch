# BSEED PM Client deployment: per-device configuration and release gates

Scope: **verified TS011F-BS-PM / TS011F_plug_1_2 PM board only**, expected firmware build pinned in the *private* campaign profile. Do not apply PM setup to non-PM switches, dimmers or an unverified board. `cli6` is not fleet-accepted merely because its OTA transport completed.

## Runbook

1. Confirm board/stock OTA tuple, exact IEEE, converter, intended role, existing load and fixture safety. Keep the historical campaign lock and private logs; do not start a new workdir to bypass an incomplete postflash campaign. Preserve one Router cohort and use the existing router-scoped join/metadata repair for a cross-role transition.
2. Configure `docs/bseed_ota_profile.example.json` privately. For PM devices, supply `pm_ssh_host`, `pm_ssh_key`, `pm_max_writes`, `pm_observe_seconds`, `pm_allow_configure` and `pm_expected_idle`. The SSH identity must be host-key verified and read-only access to the Zigbee2MQTT `database.db` must succeed; the script never writes that database. Use a private evidence directory outside git. Do not commit device IDs, IPs, private profiles, network logs or image binaries.
3. For existing flashed PM devices: `python helper_scripts/bseed_ota_campaign.py --profile PRIVATE.json --mode provision-pm --confirm-ieee EXACT_IEEE`. `provision-pm` is independently resumable; its dry-run equivalent is `python helper_scripts/bseed_pm_provision.py` with the same identity/SSH/MQTT arguments **without** `--apply`. The direct provisioner defaults to **one reporting write**; the campaign defaults to **four sequential, bounded writes** (override privately with `pm_max_writes: 1` for an unstable canary). A timeout stops all subsequent writes.
4. A future `--mode transition --confirm-ieee EXACT_IEEE` validates PM prerequisites **before** initiating the OTA, then runs scoped rejoin, targeted role metadata repair and PM provisioning before its postflash verifier. `--mode rejoin` can resume this same provisioning stage; an explicitly authorized same-role PM `--mode flash` also executes provision and postflash after successful OTA transport. No automated fixture load cycling is implied. No unexpected ZCL timeout triggers an OTA retry, reset, relay toggle or coordinator restart.
5. Independently execute `--mode postflash` (read-only) and the verified fixture in `tests/live_bseed_pm_metering.py`. A `pm_configured_candidate` and a `postflash_candidate` are **not** final hardware acceptance. Validate actual unsolicited change-to-zero reporting, physical relay behavior, HA entity parity, energy monotonicity and sustained parent/network stability before authorizing another socket.

## Provisioner invariants

The provisioner validates unique IEEE/name, actual custom model, build, endpoint-1 meter and endpoint-2 relay, cached role plus live ZDO role, bridge-online/permit-join-off, coordinator IEEE and target-only persisted scale/bind metadata. It does **not** infer device scale by copying another socket's cached values. If scale/bind metadata is missing, a single target-only `device/configure` may be explicitly enabled with `--allow-configure`; failure stops the run. In a verified state, only missing/out-of-bounds endpoint-1 PM report rows are configured, one transaction-matched bridge request at a time.

Desired report rows: activePower **10/60/5 W**; rmsCurrent **5/300/50 raw mA**; rmsVoltage **5/300/5 raw centivolts**; currentSummDelivered **10/600/1 raw Wh** (minimum/maximum/change, seconds except change). The runtime's device-specific `electricityMeter` converter must remain the source of truth for its supported metering behavior. Do not change the public fleet OTA index or configure an arbitrary ZCL cluster.

## Later read-only observations (same date)

After the provisioning run failed the initial no-load gate, an independent 85-second passive window recorded three **non-retained** MQTT samples of `power=0`, `current=0`, `energy=0.17 kWh` and approximately 241 V with no target log errors. A further 85-second strict postflash verifier returned `postflash_candidate`, including live EndDevice ZDO, correct build, standard scaled values and no target errors in that window. These observations **do not erase** the earlier intermittent relay-read timeout or prove the actual raw metrology and fixture load-to-zero behavior. Its historical campaign lock remains postflash-unverified; no image promotion.

The no-load current report has a maximum interval of 300 s. A 135 s passive check can legitimately see a stale combined current field even after power reaches zero. Accordingly `--expect-idle` now enforces at least 310 s of separated passive samples with a 330 s minimum deadline; this is an extra metering-freshness gate, not a reason to clamp or change firmware calibration. The independent physical fixture remains mandatory.
